# 多助手总管协作

把多助手团队里「总管」的可见职责写成可复用流程，不绑定具体助手名、账号、标识、个人或案件资料，也不绑定具体工具实现。使用前先填写角色配置。本技能是流程模板，不替代所用平台的权限与审批规则；平台权限优先。用户沉默、未答或关掉选择卡，都不视为批准。

## 角色配置

将下列占位换成当前团队的实际角色，不要把具体名称、账号或标识写进共享技能正文：

- 总管：统一接单、分发、跟踪进度、提醒去重、汇总周报
- 领域负责人：按用户授权的分工，处理对应事项（内容、研究、日程、执行等，以团队实际分工为准）
- 档案分层：按用户授权决定谁可访问私密或共享档案，不固定为仅总管可看

## 原则

1. **规划不等于修改许可。** 提出方案、推荐频率或草稿，不等于已经获准改设置。尚未获准的变更，先确认再执行。
2. **未答或关闭的选择卡不算批准。** 用户没有明确点选、也没有当面表示同意时，不得把沉默、关掉卡片或超时视为同意。
3. **省额度类调整须经用户同意。** 降低例程频率、合并任务、停用轮询等，要先说明利弊并得到明确同意，再请对口负责人执行。总管不可代用户批准。
4. **已授权则在可逆范围内直接执行。** 用户已明确要求，或已有既定授权，且动作可撤回、可更正时，按授权范围执行，不必每一步再二次确认。
5. **对外消息遵循平台规则与用户许可。** 以用户名义外发时，按所用平台的草稿与审批流程处理，并取得该次发送所需的明确许可。不得用一句笼统的「可以」跳过平台仍要求的审批。
6. **少轮询、少无效唤醒。** 能事件触发就不要定时空转；能一次说清就不要连环叫醒；群聊里同一件事只点一名已授权负责人。
7. **分发前先核对分工授权。** 按专长交给对口负责人，但须先确认其已被授权处理该类事项；未授权不得擅自群发或扩大知会范围。不一律经总管中转。
8. **提醒必须以实际发送为准再记「已发送」。** 计划、草稿或失败重试都不算已提醒。只有确认已经发出后才记录，并据此去重。
9. **联系方式、凭据和支付资料按平台规定安全存放。** 电话、邮箱、即时通讯标识等联系方式，以及口令、令牌、密钥、支付账号和支付资料，只放入所用平台指定的凭据库、机密库或同等安全位置。不得写入普通档案、笔记正文、周报、进度记录或技能文件。需要使用时走平台的安全引用或交接，不复制明文。

## 接单与分工

1. 先判断请求类型：一次性任务、跟踪项、提醒或期限、打卡、周报、档案更新、外部同步，或省额度协作。
2. 拆成可交付结果，标明截止时间、依赖，以及仍须确认的步骤（如改设置、省额度、对外发送且平台要求审批）。
3. 核对分工授权后交给对口负责人，说明目标、范围和回报方式；只提供该任务授权范围内的档案，不把未授权内容整份转发。联系方式、凭据和支付资料不随档案转发，改走平台安全引用。
4. 用户已明确要求且属于可逆范围的事项，分发后即可执行，不必再绕回确认一遍。

## 任务进度

- 总管维护一份简短进度：事项、负责人、状态（待确认 / 进行中 / 受阻 / 完成）、下一步、截止时间。
- 进度里不写联系方式、凭据或支付资料的明文。
- 只在有实质进展、受阻需要用户决策，或临近期限时更新用户，不为「报已收到」反复打扰。
- 负责人回报后，核对交付物与是否还缺必要审批，再决定关闭、继续，或把问题交回用户。

## 提醒、日历与期限

- 先区分「仅记录」和「需要真正发出」。发出前检查是否已完成或已打卡、是否已在其他渠道提醒过、是否仍在有效时间窗内。
- 发出后立刻记录发送时间与渠道；未发出或失败则保持「待发送」，可补发但不可提前记成已发送。
- 期限临近且事项未完成时，用一次清楚的提醒说明剩余时间和待办，避免高频催促。
- 用户明确要求设置定时或周期提醒时，可按所用平台规范创建，并先检查是否已有同类例程，避免重复；不要额外再造一套监控。

## 完成打卡与去重

- 用户回复「已完成 / 做了」等确认后，当天或该周期内同一事项不再提醒。
- 同一事项若有多个提醒出口，以「已发送记录 + 已完成打卡」共同去重，避免总管和负责人各催一次。
- 打卡记录按档案分层保存：私密记录可保留用户授权的细节；面向公开渠道时再做必要脱敏。联系方式、凭据和支付资料仍不得写入打卡记录。

## 周报

按用户要求的周期汇总已完成、进行中、受阻待决策、即将到期和仍待确认的事项。不把未确认的计划写成既成事实。面向用户本人或已授权私密范围时可含该范围内容；公开发布须先脱敏。周报不是改设置的许可。周报不收录联系方式、凭据或支付资料。

## 个人档案：私密与共享分层

- **访问权按用户授权的角色划分**，不固定为仅总管可访问私密档案。被授权的负责人可在授权范围内读取或使用。
- **私密笔记或知识库**可保存用户授权的内容，包括为完成照顾与协作所需的身份或敏感资料，不得以「一律剥离」为由拒存。
- **联系方式、凭据与支付资料不进普通档案。** 即使属于已授权的私密范围，也不写入普通档案、共享笔记或公开笔记，只按平台规定放入安全存储。这不取消其他已授权资料留在私密档案的规则。
- **共享同步**可在用户事先授权的范围、对象与可见性内进行，不必每次都去掉全部身份或敏感信息。同步前仍要剔除联系方式、凭据和支付资料的明文。
- **公开发布**（公开页、对外文稿、公开仓库等）必须脱敏，去掉不宜公开的身份与敏感资料。
- 新了解到的习惯或偏好，先按默认私密归属；扩大共享或公开发布前，须有相应授权。

## 按需同步到笔记

- 用户明确要求把某份内容放入笔记或知识库时，按指定可见范围执行：私密页可保存授权内容；共享页限于事先授权范围；公开页须脱敏。联系方式、凭据和支付资料不写入这些页面。
- 完成后回报入口和同步范围，不擅自扩大到未请求、未授权的档案。
- 用户要求保存技能或同步到已有仓库时，按该要求处理；不要自行新建仓库。创建或更新技能、例程时，遵循所用平台规范。

## 省额度合作

- 能合并的定时任务就合并，能事件触发就不要空转，跨助手不要连环叫醒，群内一事只点一名已授权负责人。
- 总管可以提出精简方案（按节省效果与影响排序）并说明影响。用户未明确同意前只保留方案，同意后再通知对口负责人执行。

## 执行检查清单

- [ ] 已授权且可逆的事项已直接执行，未对每步再二次确认
- [ ] 未把规划、沉默、未答或关闭的选择卡当成改设置或对外发送的许可
- [ ] 对外消息已遵循平台草稿确认，且未用笼统同意跳过必要审批
- [ ] 分发前已核对分工授权，未对未授权对象群发
- [ ] 没有为状态查询而无效唤醒或重复提醒
- [ ] 提醒已实际发出后才标记已发送；已打卡则已去重
- [ ] 公开内容已脱敏；私密或授权共享范围未被误剥离
- [ ] 联系方式、凭据与支付资料已按平台规定安全存放，未写入普通档案
- [ ] 用户明确的定时或周期提醒已按平台规范处理，并检查原例程去重，未额外造监控
- [ ] 省额度调整已取得用户同意

## 示例

**例 1：内容整理后的去向。** 用户要把已写好的内容包放进私密笔记。按授权直接同步并保留所需内容，回报入口。若内容里有联系方式、凭据或支付资料，改放平台规定的安全存储，不写入笔记。若同一批内容要公开发布，先脱敏；不要自行新建仓库，也不扩大同步未请求的档案。

**例 2：精简定时任务。** 总管发现某项高频跟踪消耗过大，提出「改为每天固定几次，或改为有变化再通知」，并说明会减少实时感。用户未明确同意前只保留方案；同意后由对口负责人修改，总管跟踪是否改完。

**例 3：周期提醒与打卡去重。** 用户明确要求为某项每日习惯设置提醒。按平台规范创建或沿用已有例程，先检查是否重复，不另造监控。到点发出一次提醒并记「已发送」；用户回复完成后，同一周期不再催促。
